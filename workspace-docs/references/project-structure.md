# 项目目录设计

## 从上下文提取项目简报

- 提取当前目标、交付物、读者或维护者、业务模块、运行或交付入口、已有约束。能从当前对话、用户附件和仓库确定的信息标注来源。把事实、工作假设和待确认项分开。
- 用户描述期望，仓库反映当前状态。冲突时列出差异，按目标结构与现有依赖分别处理。无法访问仓库时给出可调整的方案，并标注尚待检查的依赖。
- 对会改变项目边界的缺口，例如单服务与多服务、源数据与衍生数据的权限边界，优先用已知信息核实。仍有歧义时给出暂定方案，或向用户确认具体的边界。

## 设计目录

1. 查找已有规则、入口和约定。代码项目查看构建配置、模块与测试、CI、部署和发布路径。文档或业务项目查看文档入口、项目或话题、素材、交付件和归档方式。
2. 按实际边界分组。共享部署生命周期的后端与模型能力可先放在同一服务内。确有独立运行、发布或维护边界时再拆应用或服务。数据分析项目可按输入、处理、输出区分，权限受限的原始数据用受控入口引用。
3. 为新增目录说明归放对象和入口。优先采用工具链和团队已有约定。空目录只在工具要求或用户明确需要时纳入方案。
4. 交付目录树、关键依据和典型文件的归放示例。已有项目同时给出保留、迁移和暂缓项。

## 优化已有结构

- 方案任务交付目录树与迁移映射。用户要求执行时，先核对未提交改动、目标冲突及路径依赖。
- 移动前查找导入、配置、构建与测试入口、CI 路径过滤、部署脚本及文档链接。按组更新，保留必要的兼容入口。文档迁移另见 [归档与迁移](filing-and-migration.md)。
- 根据改动运行相关检查，例如最小构建、相关测试、文档预览或链接校验。交付记录已验证入口、待验证项和涉及的回退步骤。

## 从对话推导目录的合成案例

输入是「做一个内部采购问答服务。HTTP API 和检索随同一镜像发布。我们有评测集，采购原始附件要放在受控存储」。仓库已存在 `app/main.py` 和以它为入口的容器配置。

| 提取结果 | 结构决定 |
| --- | --- |
| API 与检索同镜像发布，现有入口是 `app/main.py` | 保留 `app/` 和入口，检索实现按需进入 `app/retrieval/`。 |
| 已有评测集，评测可单独运行 | 用 `evals/` 放评测脚本、允许提交的测试样本和数据集版本索引。 |
| 采购附件在受控存储 | 在项目文档记录访问入口、权限要求和版本标识。 |
| 使用方需要查部署与验收 | 将部署手册放到 `docs/`，在根 README 链接部署和评测入口。 |

如果后续确认评测有独立发布流程，再决定是否拆成独立组件。若仓库已有 `benchmarks/` 且 CI 依赖该路径，优先复用。缺少仓库时把上述目录标记为建议，并把容器入口和 CI 依赖列为待核实。

## 迁移批次的验收

每批记录旧路径、新路径、调用方和验证方式。例如移动评测脚本时，同时检查 CI 命令的工作目录、测试数据相对路径及报告上传路径。改动前先记录可运行的入口，迁移后用同一入口或它的明确替代项验证。如果有外部任务仍使用旧路径，先保留兼容入口或暂缓迁移，并记录后续切换条件。
